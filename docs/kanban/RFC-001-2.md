# Contractor — migrar DTOs para entidade direta

## Contrato de Entrada
- `POST /partners/{partnerId}/contractors`: `{ name: string (max 255), document: string (max 32) }`.
- `PATCH /contractors/{id}`: `{ name?: string (max 255) }`.
- `partnerId`: ID prefixado do Partner (`prt_...`).

## Contrato de Saída
- `GET /partners/{partnerId}/contractors`, `GET /contractors/{id}` e respostas de POST/PATCH serializam a entidade `Contractor` no grupo `contractor:get`: `id` (`cnt_...`), `name`, `document`, `active`, `createdAt`.
- `404` para Partner/Contractor inexistente ou soft-deletado; `409` para documento duplicado.

## Requisitos de Qualidade
- [x] Integração: `ContractorApiTest` verde (collection/GET/PATCH/404, escopo por parceiro)
- [x] Unitário: `ContractorRegistrar` valida documento duplicado; `Contractor` aceita `setPartner()` fluente

## Restrições Técnicas
- Mover o `#[ApiResource]` (e operações) de `ContractorResource` para a entidade `Contractor` com `#[Groups]`.
- Remover `ContractorInput`, `ContractorOutput`, `ContractorPatchInput` e `ContractorResource`.
- Subresource POST usa `provider: CreateProvider::class` + `Link`; construtor sem `Partner`.
- Providers passam a retornar `Contractor` (não `ContractorOutput`); processors recebem `Contractor`.
- Seguir o padrão de `Partner`/`Project`.
